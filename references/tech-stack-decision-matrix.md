# 技术栈选型决策参考 (Tech Stack Decision Matrix)

技术选型应基于具体的工程约束，避免因追逐新潮引入不必要的复杂依赖。评估的核心维度包括：冷启动时延、内存开销、二进制/分发体积、吞吐能力、生态成熟度与跨平台表现。

---

## 1. 命令行工具与自动化系统 (CLI & Tooling)

| 场景与硬性量化指标 | 推荐技术栈 | 量化基线 (Benchmark) | 架构理由与妥协代价 |
|---|---|---|---|
| **跨平台运维 / 离线 Agent 工具 / 敏捷业务** | **Python 3 (标准库优先) + Typer/Argparse** | 冷启动 ~50-100ms；内存基线 ~15-30MB；源码直跑免编译 | 优势：跨平台表达力极强，无编译周期；代价：依赖宿主机 Python 解释器环境 |
| **单文件分发 / 高频执行 / 工具分发** | **Go + Cobra** | 冷启动 < 10ms；内存基线 < 10MB；单二进制体积 10-25MB | 优势：静态交叉编译极简，秒级构建分发；代价：泛型与领域建模表现力偏朴素 |
| **极致性能 / 系统底层 / 资源受限环境** | **Rust + Clap** | 冷启动 < 5ms；内存基线 < 5MB；单二进制体积 3-10MB (stripped) | 优势：内存安全零运行时，CPU 吞吐极高；代价：借用检查学习曲线陡峭，编译耗时较长 |
| **Node.js 前端团队内部工作流** | **Node.js + Commander / CAC** | 冷启动 ~80-150ms；内存基线 ~30-50MB；依赖体积 ~5-20MB | 优势：与 Web 前端同构，NPM 生态成熟；代价：node_modules 体积大，受宿主机 Node 影响 |

### CLI 量化决策分流
- 约束条件：**宿主机不可保证 Python/Node 环境，且冷启动必须 < 20ms** -> 强制判定为 **Go**（或 Rust）。
- 约束条件：**开发周期极紧，主要在内网工程师环境执行，需快速解析复杂业务数据** -> 强制判定为 **Python 3**。

## 2. 后端服务端与 API (Backend & APIs)

| 场景与量化性能指标 | 推荐技术栈 | 量化基线 (Benchmark) | 架构理由与妥协代价 |
|---|---|---|---|
| **AI 应用 / 数据服务 / 业务敏捷型 API** | **Python + FastAPI + Pydantic + Uvicorn** | 单实例 QPS ~2,000-5,000；P95 延迟 < 50ms；内存驻留 ~60-120MB | 优势：与 AI/数据生态原生打通，数据校验与 OpenAPI 全自动；代价：CPU 密集计算需进程池规避 GIL |
| **高并发网关 / 微服务基础设施 / 流式管道** | **Go + Gin / Fiber / Chi** | 单实例 QPS ~30,000-80,000；P95 延迟 < 5ms；内存驻留 ~15-35MB | 优势：超低内存开销，Goroutine 高并发，部署体积极小；代价：手写错误处理样板代码较多 |
| **全栈轻量同构 / BFF 服务** | **Node.js / Bun + Hono / NestJS** | 单实例 QPS ~10,000-25,000；P95 延迟 < 15ms；内存驻留 ~40-90MB | 优势：前后端 TypeScript 类型零成本共享；代价：单线程事件循环阻塞防御要求高 |
| **企业复杂领域驱动业务 (DDD)** | **Java/Kotlin + Spring Boot 3** | 单实例 QPS ~15,000-30,000；启动内存 > 200MB；JVM 预热后稳定 | 优势：事务治理与企业级中间件无可匹敌；代价：冷启动慢（除非 GraalVM Native），内存开销大 |

## 3. Web 前端应用 (Web Frontend)

| 场景与量化基线 | 推荐技术栈 | 量化基线 (Benchmark) | 架构理由与妥协代价 |
|---|---|---|---|
| **复杂企业中后台 / 协作系统 (长期演进)** | **React 18/19 + TypeScript + Vite + Tailwind** | 首屏 JS Bundle ~150-300KB (gzip)；首屏 FCP < 1.2s | 优势：组件生态最繁荣，人才储备最丰富；代价：状态管理库与工程配置易发散 |
| **轻快业务看板 / 敏捷交付中台** | **Vue 3 + TypeScript + Vite + Pinia** | 首屏 JS Bundle ~100-200KB (gzip)；首屏 FCP < 1.0s | 优势：响应式心智负担低，SFC 集中度高，官方工具链统一；代价：大型顶尖设计系统库略少于 React |
| **内容门户 / 营销站 / SEO 强约束** | **Next.js / Astro (SSG/SSR)** | Lighthouse 性能评分 > 95；首屏 TTFB < 200ms | 优势：首屏秒开，搜索引擎友好；代价：必须具备 Node 运行环境或边缘托管支持 |
| **超轻量嵌入式 / 无框架纯静态工具** | **Vanilla TS + HTML5 + CSS3 + Vite** | 首屏 JS Bundle < 20KB (gzip)；首屏 FCP < 0.3s | 优势：零框架运行时开销，打包极小；代价：复杂双向绑定与深层状态流转需手写管理 |

## 4. 持久化与存储层 (Storage & Persistence)

| 场景与量化要求 | 推荐技术栈 | 选型标准与量化界限 |
|---|---|---|
| **单机应用 / CLI 本地状态 / 嵌入式服务** | **SQLite (WAL 模式)** | 数据量 < 50GB；写入并发 < 2,000 QPS；单文件零运维；支持完整 ACID |
| **通用关系业务 / 高并发事务** | **PostgreSQL** | 数据量 > 50GB；读写并发 > 5,000 QPS；JSONB 高性能支持；工业级可靠性 |
| **高吞吐缓存 / 瞬态状态** | **Redis** | 毫秒级延迟；纯内存存储；支持丰富数据结构与分布式锁 |
| **静态配置 / 本地轻量记录** | **JSON / YAML + 原子重命名写入** | 数据大小 < 5MB；低频变更；对 Git 版本追踪友好 |

## 5. 架构分层约束

1. **模块化单体优先 (Modular Monolith First)**：在业务规模与团队协作尚未出现明显瓶颈前，优先采用模块化单体，避免过早拆分微服务带来的运维复杂性。
2. **三层单向依赖架构 (Strict Directional Dependency)**：
   - `Presentation` -> `Domain/Service` -> `Infrastructure`。
   - 严禁基础设施层反向引用领域层实现，严禁展现层绕过服务层直接读写存储层。
